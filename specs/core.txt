Jules Agent Prompts for Epic 1: Core Player Experience & Motivation Engine (MVP)
This document contains a series of prompts for the Jules Agent, designed to systematically build the features outlined in Epic 1. Each prompt corresponds to a specific task and is structured to follow Clean Architecture principles, ensuring a clear separation of concerns, maintainability, and testability.
You will organize the backend code into the following layers:
/packages/api/src/domain: Contains core business logic, including entities and use cases. This layer has no dependencies on any other layer.
/packages/api/src/application: Contains application-specific logic, like controllers that orchestrate the flow of data from the web to the use cases.
/packages/api/src/infrastructure: Contains all external concerns, such as database implementations (Mongoose Repositories), web frameworks (Express routes), and other third-party integrations.
Task 1.1.1.1: Define Task Entity and Data Persistence Layer
Prompt:
You are Jules, an AI software engineer. Your goal is to define the Task entity and set up its persistence layer according to Clean Architecture principles.
Context:
The Task entity is the foundational data model for all user-trackable items. We will define its pure domain representation first, then create the database-specific implementation.
Specifications:
Domain Layer:
In /packages/api/src/domain/entities/, create task.entity.ts. Define a Task class or interface that represents a task with its properties (id, user, type, text, notes, isPositive, isNegative, completed, streak). This should be a plain object with no Mongoose-specific code.
In /packages/api/src/domain/repositories/, create task.repository.ts. Define a ITaskRepository interface with methods like create(task: Task): Promise<Task> and findById(id: string): Promise<Task | null>.
Infrastructure Layer:
In /packages/api/src/infrastructure/database/mongoose/models/, create task.model.ts. Define and export the taskSchema using Mongoose, including all fields, types, and timestamps as originally specified. This is the concrete database model.
In /packages/api/src/infrastructure/database/mongoose/repositories/, create task.repository.impl.ts. This class will implement the ITaskRepository interface, using the Mongoose Task model to perform the actual database operations.
Testing:
Write new unit tests for any business logic within the Task entity itself (if any).
Your repository implementation does not require unit tests at this stage, as it will be tested via integration tests later.
Mandatory Guidelines:
You must follow all guidelines specified in GEMINI.md.
You must adhere to Clean Architecture and SOLID principles. The dependency rule is key: Domain must not know about Infrastructure.
After implementing the changes, you MUST run the appropriate build and test commands.
Task 1.1.1.2: Implement Task Creation and Completion Use Cases and API Endpoints
Prompt:
You are Jules, an AI software engineer. Your task is to implement the core business logic for creating and completing tasks and expose it via API endpoints.
Context:
This involves creating use cases (interactors) for each action, which will be called by controllers. This separates the business rules from the web delivery mechanism.
Specifications:
Domain Layer (Use Cases):
In /packages/api/src/domain/use-cases/task/, create create-task.use-case.ts. The use case class will have an execute method that takes task data, creates a Task entity, and uses the ITaskRepository (injected via constructor) to save it.
In the same directory, create complete-task.use-case.ts. Its execute method will find a task by ID and handle the completion logic. For now, this is a simple state change.
Application Layer (Controllers):
In /packages/api/src/application/controllers/, create task.controller.ts. This controller will have methods for createTask and completeTask. Each method will instantiate and execute the corresponding use case and return the appropriate HTTP response.
Infrastructure Layer (Routing & DI):
In /packages/api/src/infrastructure/web/routes/, create task.routes.ts. Implement the POST /api/tasks and POST /api/tasks/:id/complete endpoints, linking them to the TaskController methods.
Ensure your dependency injection setup provides the concrete TaskRepositoryImpl to the use cases when they are invoked.
Testing:
Write comprehensive unit tests for CreateTaskUseCase and CompleteTaskUseCase.
You MUST use a mock implementation of ITaskRepository to test the use cases in isolation from the database.
Mandatory Guidelines:
Follow all guidelines in GEMINI.md and adhere to Clean Architecture and SOLID principles.
Run build and test commands to ensure all new and existing tests pass.
